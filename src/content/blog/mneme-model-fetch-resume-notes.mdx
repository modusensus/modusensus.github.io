## 00 · 症状：下载 900MB，失败在 890MB，然后从头再来

dsh-mneme 用 transformers.js 跑本地嵌入和重排模型，首次加载要下载 `model.onnx`——1GB 上下的大文件，走 transformers.js 自己的 `env.fetch`。

弱网下的故障模式非常整齐：undici 的 socket 中途被重置，整个下载抛 `TypeError: terminated`，**已收的字节全部作废，下次从第 0 个字节重来**。网络每抖一次，进度就清零一次——理论上可以永远到不了终点。

修复没有去动 transformers.js：4.2.0 的 `env.fetch` 是官方文档化的可替换点，于是一整层"带断点续传的 fetch"做在了这一层——对 transformers.js 而言它仍然是一个普通的 fetch，**成功路径的语义一点没变，所有变化都发生在失败路径**。

```
普通 fetch：  失败 = 丢掉一切，从 0 开始
韧性 fetch：  失败 = 已收字节落进磁盘 .part，重试从断点继续
              （包括换一次进程、下一次启动）
```

## 01 · 断点怎么续：Range 与 If-Range

续传的 HTTP 语义本身不复杂——带 `Range` 头请求剩余字节：

```js
if (offset > 0) {
  headers.set("Range", `bytes=${offset}-`);
  // 断点对应的内容若在服务端被换过，服务器会回 200（全量）而不是 206
  const storedEtag = readMeta(metaPath);
  if (storedEtag) headers.set("If-Range", storedEtag);
}
```

复杂的是每个返回值背后"该信什么"：

```
首次下载
  GET ──▶ 200 + content-length + etag
  字节流追加写进 sha256(url).part
  中断 ──▶ 已收字节留在磁盘上，这就是断点

重试（同进程或下一次启动都行）
  GET  Range: bytes=N-   If-Range: <旧 etag>
    ├─ 206 ──▶ 服务器确认从 N 续：把新字节拼上去
    ├─ 200 ──▶ 内容变过了：断点作废，整份重来
    └─ 416 ──▶ 断点比源文件还大：作废，从 0 开始
```

> 坑 ①：**不带 If-Range 的续传是静默损坏**。断点对应的内容如果在服务端被换过（模型发布方更新了文件），服务器会正常从你要求的位置继续——旧断点拼上新内容，得到一份校验都未必拦得住的坏模型。If-Range 就是给服务器的一句确认："内容没变才续，变了就给我全量"。**宁可整份重来，不可拼错。**

> 坑 ②：**416 不处理，会烧光全部重试次数**。断点比源文件还大（通常来自被替换前的旧文件）时，Range 请求会得到 416。不特判的话，每次重试都 416，最后抛给用户一条看不懂的错。正确动作是清掉断点、这次尝试作废、下次从 0 开始。

还有一个更刁钻的：206 回来了，但 `Content-Range` 显示服务器续的起点和本地断点对不上。**不猜，清掉重来**——拼错的字节比下载失败更糟。

## 02 · 给下游的响应：永远规范的 200

这是整个实现里最重要的决定：**断点拼接是我们内部的事，一个字节都不能漏给下游**。

transformers.js 的 hub 层把非 200 一律当失败处理。如果图省事把 206 直接透传，下游会认为请求失败——续传做得再好也是白搭。所以内部拼完断点后，交给下游的永远是一份规范的响应：`200` + 完整 `content-length`，body 从磁盘流式读出（1GB 不进内存）：

```js
return new Response(Readable.toWeb(nodeStream), {
  status: 200,
  headers: {
    "content-type": "application/octet-stream",
    "content-length": String(size),
  }
});
```

> 坑 ③：**适配层的第一守则是不改变成功路径的语义**。下游代码是按标准 HTTP 语义写的，任何"看起来更好"的优化（透传 206、省掉 content-length）都是在替下游做它没同意的决定。

## 03 · 单写者锁：两个进程写同一份 .part 是写损坏

断点文件要跨进程、跨重启复用，命名就得内容寻址——`sha256(url)`，而不是 pid。于是必然出现并发：两个进程（两个终端各开一个 agent）同时下载同一个模型，各自往同一份 `.part` 追加字节——**这不是竞争条件，这是写损坏**。

解法是文件锁，三板斧：

```js
// 1. 独占创建：抢不到 = 有人在写
const fd = openSync(lockPath, "wx");
writeSync(fd, String(process.pid));

// 2. 过期偷锁：活着的话，每个进度节拍都会刷新锁的 mtime
const age = Date.now() - statSync(lockPath).mtimeMs;
if (age > STALE_LOCK_MS) { rmSync(lockPath); /* 再抢一次 */ }

// 3. 进度节拍刷新锁的"活着证明"
futimesSync(lockFd, new Date(), new Date());
```

三个细节各有道理：

- **抢不到锁就放弃落盘，按现状裸转发**。另一个进程正在下同一个文件，让它正常下完就是了——这边的这次请求原样透传给底层 fetch，语义与没有这层时完全一致。
- **偷锁只试一次**。再抢不到就放弃。锁机制必须永远有"退回旧行为"的出口，不能让一个锁故障把下载堵死。
- **锁的释放时机跟着响应体走**。失败路径在 catch 里释放；成功路径的锁要等下游把响应流读完、断点文件使命结束时才清理——若在返回响应时就放锁，另一个进程会在「`.part` 还被下游流读着」的窗口里动它。

> 坑 ④：**锁的"活着证明"和进度是同一件事**。持锁方每个进度节拍刷新锁文件的 mtime，偷锁方用 mtime 判断死活——不需要心跳协议，磁盘时间戳就是心跳。

## 04 · 看门狗：计"连续无字节"，不计总时长

超时控制最容易做错的一件事：设总时长上限。几百 MB 到 1GB 的文件在慢网下**合法地**要下几十分钟，总时长上限会掐死健康但慢的下载。

真正的故障信号是**僵死**：连接还在，但连续很久一个字节都没有。所以看门狗计的是"连续无字节"：

```js
const armIdle = () => {
  clearTimeout(idleTimer);
  idleTimer = setTimeout(
    () => controller.abort(new Error(`连接空闲超过 120s 无数据`)),
    idleTimeoutMs
  );
};
armIdle();                       // 建立连接时上膛
// 读循环里，每收到一块字节：
armIdle();                       // 重新计时
```

> 坑 ⑤：**服务器"干净地"提前关流也是断流**。socket 正常关闭（不抛错），但 `offset + received !== total`——字节没给够。不核对 content-length 的话，一份不完整的模型会以"下载成功"的姿态落进缓存。**完成与否的判据是字节数，不是"流结束了"这个事件。**

## 05 · 失败信息里必须有"中断在哪"

重试全部失败后抛出的错误，必须带上位置：

```
模型文件下载失败（试了 3 次，中断于 37%（388.2MB/1.0GB））：
连接空闲超过 120s 无数据
```

issue #194 的原始报告里有一条很朴素的要求：用户要能区分**是网络断了还是磁盘满了**，而不是看到一句干巴巴的 `TypeError: terminated`。百分比和字节数就是为此存在的——顺便，退避用 1s → 2s → 4s（封顶 15s），给网络一点自愈的时间。

## 06 · 速查表

| 场景 | 信号 | 动作 |
| --- | --- | --- |
| 正常续传 | 206 + Content-Range 起点吻合 | 从断点拼接 |
| 服务端内容已变 | 200（If-Range 判定） | 清断点，整份重来 |
| 断点超过源文件大小 | 416 | 清断点，从 0 开始 |
| 续传起点对不上 | 206 但偏移不一致 | 清断点，不猜 |
| 连接僵死 | 120s 连续无字节 | abort，断点保留，退避重试 |
| 服务器提前关流 | `received ≠ content-length` | 视为失败，断点保留 |
| 另一进程在写 | 抢不到锁 | 裸转发，不参与落盘 |

最后回到那个最值得学的视角转换：这个功能没有 fork transformers.js，没有魔改下载器，只是**在官方文档给的那个替换点上，把"失败"重新定义了一遍**。成功路径原封不动，失败路径从"丢弃一切"变成"保留进度"——很多韧性工程的本质，就是把系统对"失败"的默认反应从遗忘改成记账。
