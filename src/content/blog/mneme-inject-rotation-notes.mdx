## 00 · 问题：好记忆也不该每轮都背同一句台词

dsh-mneme 每一轮对话都会往 system prompt 里注入几条"此刻最相关"的记忆。最近相关通常很稳定——同一个项目聊上二十轮，那五条"最相关"可能二十轮都不变。

社区用户（[Philia-FY](https://github.com/Philia-FY)）在 issue #205 里指出了这件事的另一面：**注入位是稀缺资源，同一批记忆长期霸占它，别的记忆就永远没有出场机会**。他建议跨轮轮换：最近几轮注入过的，本轮靠后站。

听起来是个小需求。真做起来，埋了三个语义坑。

## 01 · 注入管线，三十秒版

先交代注入是怎么发生的。每一轮渲染时，`injectCandidates` 按优先级把几路召回合并成一个小池子：

```
用户查询向量召回（语义）        ┐
缓存的语义召回（上一轮结果复用） ├─▶ 合并去重 → 排序 → 取 maxItems 条注入
BM25 词面召回（首轮兜底）       │
静态排序（无查询时的保底）      ┘
```

有个约束值得先说：**渲染必须是同步的**——宿主的 system prompt 装配不等任何异步操作。所以查询向量是异步预取进缓存的，渲染时只能用缓存里已有的；首轮向量没到，就由 BM25 兜底。这是设计事实，不是 bug，但决定了后面很多写法。

## 02 · 轮换的语义：「一轮」怎么数

第一个设计决定：**窗口的单位是"不同的用户查询"，不是"渲染次数"**。

为什么有区别？同一个用户查询下，agent 可能连续执行多个工具调用，每次工具调用后 system prompt 都会重新装配、注入逻辑都会重新执行。如果按渲染次数数窗口，一次带五个工具调用的回答会把窗口自己推走五格——用户明明只问了一句话。

所以历史记录按「查询 → 本轮注入的 id 集合」存，同一个查询的重复渲染**覆盖**上一条而不是追加：

```js
function recordInjection(sessionId, query, candidates) {
  const deque = rotationHistory.get(sessionId) ?? [];
  const ids = new Set(candidates.map((c) => c.id));
  const last = deque[deque.length - 1];
  if (last && last.query === query) {
    last.ids = ids;      // 同一查询的重复渲染：覆盖本轮内容，不推进窗口
  } else {
    deque.push({ query, ids });
  }
}
```

窗口数的是**用户问了几个不同的问题**，不是系统渲染了几次。

## 03 · 别拿本轮转本轮

第二个坑是我们的回归测试抓的：**窗口里混进了当前轮自己的集合**。

设想第二轮：窗口 N=2，历史里躺着第一轮和第二轮自己的记录。计算"最近两轮注入过什么"时，如果把第二轮自己也算进去，那么本轮的候选会"因为被本轮注入过"而被降权——**自己和自己轮换**，窗口形同虚设。

修法是一行语义修正：计算窗口时只看**之前的轮次**，排除与当前查询相同的条目：

```js
// 只看"之前的轮次"：同一查询的重复渲染不该拿本轮自己的集合来转自己
const prior = query ? deque.filter((e) => e.query !== query) : deque;
```

> 坑 ①：**"最近 N 轮"的窗口语义里，藏着"含不含当前轮"这个自由度**。不显式排除，窗口就会悄悄包含自己。测试先行在这里救了命——先写断言（第三轮的注入必须不同于前两轮的并集），实现里的自我轮换当场现形。

另一个易漏点：窗口取的是最近 N 轮的**并集**。第三轮要避开的是第一轮加第二轮注入过的全部 id，不是只有上一轮。

## 04 · 池子不扩，轮换越不出箱子

第三个坑最隐蔽，而且不是我们发现的——是 Philia-FY 在实现合入后读源码读出来的。

候选池原本有个固定容量：`maxItems × 2`。注入 5 条，池子 10 条。这个数字在"每轮取前 5"的时代没问题；轮换进来后，数学变了：

```
maxItems = 5，窗口 N = 2，池子 = 10
前两轮最多注入 5 × 2 = 10 条 —— 恰好是整个池子
第三轮：池子里 10 条全部在"最近注入"名单上 → 新鲜候选 = 0 → 轮换静默失效
```

**窗口要的牌，比池子装的多——轮换越不出这个箱子**，而且失效得无声无息：不报错、不降级，注入照常发生，只是永远轮不动。

修法是把池子跟窗口挂钩：

```js
const poolSize = rotateWindowN > 0
  ? Math.max(maxItems * 2, maxItems * (rotateWindowN + 1))
  : maxItems * 2;
```

窗口 N=1 时池子不变（N+1=2，正好等于旧的 2 倍）；N=2 时 15 条；N=4 时 25 条。四个固定容量的位置——列表查询上限、向量召回 limit、BM25 召回上限、合并断点——全部跟着这个数走，一处都不能漏。

> 坑 ②：**给既有行为加"换一批"语义时，容量约束要跟着重新算**。旧常量（2 倍池）在旧语义下是拍脑袋的安全余量，在新语义下是硬上限。更值得记的是：这个坑来自用户读源码，不是来自运行报错——**语义层面的失效往往不炸，只是悄悄不工作**，读码的读者有时比测试更快。

## 05 · 兜底：没有新鲜牌时，保持原样

轮换不能为了轮而轮。如果池子里真的没有新鲜候选（库就那么大，或者窗口开得太大），行为应当退回原来的选择——**宁可重复，不要为了凑新鲜把不相关的记忆硬塞进上下文**：

```js
const fresh = candidates.filter((m) => !rotate.has(m.id));
if (fresh.length > 0) {
  candidates = [...fresh, ...candidates.filter((m) => rotate.has(m.id))];
}
// fresh 为空 → 什么都不做，原样返回
```

有新鲜牌时，新鲜的排前面、注入过的补位殿后；没有时，维持既有行为。轮换是"优先级重排"，不是"强制替换"。

## 06 · 参数与速查

配置项 `injectRotationTurns`：最近 N 个不同查询轮次注入过的记忆本轮靠后，0 = 关闭（默认，保持既有行为）。

| maxItems | 窗口 N | 旧池（2×maxItems） | 新池（maxItems×(N+1)） |
| --- | --- | --- | --- |
| 5 | 1 | 10 | 10（持平） |
| 5 | 2 | 10 | 15 |
| 5 | 4 | 10 | 25 |

三条设计决定一句话版：

1. **按"不同的查询"数轮次**——工具调用的重复渲染覆盖不推进；
2. **窗口只看之前的轮次**——别拿本轮转本轮，取的是最近 N 轮的并集；
3. **池子跟窗口挂钩**——要多少新鲜牌，就得备多大的池子；没有新鲜牌时保持原样。

一条更普适的收尾：这三个坑，一个藏在定义里（什么是一轮），一个藏在时序里（谁算"之前"），一个藏在容量里（池子多大）。**轮换这类"重排旧结果"的功能，危险从不在排序本身，而在它依赖的那些隐含假设。**
